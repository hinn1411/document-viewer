# T09: Parallel calls with a deadline
P2 · est 4 h · done · 2026-11-01

**Why:** FR2, NFR1, NFR2 → without it nothing calls the adapters: a user would wait for both sources in turn, and one slow or broken source would fail the whole search.

## Done when
1. Given two sources that each take 1 s, when `search(vin)` runs, then it finishes in under 1.5 s, because the calls run in parallel.
2. Given a source that takes 5 s, then `search` returns within 2.5 s, with the other source `OK` and this one `UNAVAILABLE` with reason `TIMEOUT` and at least 2 s spent waiting.
3. Given one source throws, then the other source's documents are still returned, and the result is `PARTIAL`.
4. Given any mix of results, including an unexpected exception, then every source ends as exactly one `SourceOutcome` with its latency, in source order, and no exception from a source reaches the caller. `SourceException` keeps its reason; anything else is `ERROR`.

## Tests (written first)
- `DocumentSearchServiceTest` (fake sources): `callsSourcesInParallel` (#1), `timesOutSlowSourceAt2s` (#2), `oneFailureDoesNotHideOtherSource` (#3), `everySourceEndsWithAResult` (#4)
- `DocumentSearchIT.serviceTimeoutGivesPartialResult`: real adapters and WireMock with demo VIN `…000002`: Sales `OK`, Service `UNAVAILABLE` with `TIMEOUT`, `PARTIAL`, within 2.5 s (#2)

## Decisions
| Question | Answer | Source |
|---|---|---|
| Shape | `search(Vin)` returns `DocumentSearchResult` from `ResultMerger`. `FAILED` is a result here; T12 maps it to 503. `Caller` arrives with T10 | 05, 06 T06 |
| How | One `CompletableFuture` per source on a virtual-thread executor, with `completeOnTimeout` at `docviewer.source-deadline` (2 s) | 06 T09, 01 |
| Past the deadline | The search stops waiting and ignores a late answer. The call isn't cancelled: a stalled call ends at the adapter's read timeout, and a trickling one runs on until the source finishes. A timed-out outcome's latency is the deadline | default; 01 |
| `Clock` | Not injected yet: nothing here reads the time, and latency uses `System.nanoTime()`. T11 adds it for the fallback age. 06's "fixed `Clock`" waits until then | java-code rule |
| Fake source delay | Waits on a latch with a timeout, not `Thread.sleep`; `@AfterEach` releases it, so no thread outlives its test | testing rule |
| IT setup | Small Spring context with both adapters, no PostgreSQL, as in the adapter ITs. The adapter's 1.5 s read timeout reports `TIMEOUT` first here | T07; 06 T09 |
