# T11: Fallback snapshots
P3 · est 3 h · agreed · 2026-11-01

**Why:** NFR2, A8 → without it a source outage shows the user nothing, even when a recent copy of those documents could be served with a clear label.

## Done when
1. Given a source answers within its deadline, then its documents are saved as a snapshot on a background thread, once the audit is saved. An empty list is saved too, because "no documents" is a real answer.
2. Given Service fails and a 3-hour-old snapshot exists, then Service is `STALE` with its failure reason, its documents have `stale: true`, `dataAsOf` is the snapshot time, and the result is `PARTIAL`.
3. Given only a 25-hour-old snapshot, then Service is `UNAVAILABLE`.
4. Given reading the snapshot fails, then Service is `UNAVAILABLE` with its original reason, and the search still returns.
5. Given saving the snapshot fails, then the response is unaffected, and the log names the source and exception class but not the VIN.
6. Given an older save finishes after a newer one, then the newer copy is kept. Documents read back equal the documents saved.
7. Given the hourly cleanup job runs, then snapshots older than 24 h are deleted and newer ones stay.
